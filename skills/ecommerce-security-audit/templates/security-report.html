Action required before you rely on this

Set up your security alerts email

The automatic checks only protect you if their alerts reach you. Set up one dedicated email address to receive every security alert — vulnerable packages, failed scans, and fixes to approve — and route the sources to it. Do this before moving on.

  1. Create or choose a dedicated alerts address (e.g. security@yourdomain) that you'll actually check.
  2. In GitHub → Settings → Notifications, set that address and turn on Actions + Dependabot email alerts.
  3. In each repo → Settings → Code security, enable Dependabot alerts + security updates.
  4. (Recommended) add a free error-monitor (e.g. Sentry) and send its alerts to the same address, so live errors reach you too.

Honest note: these reliably alert you to vulnerable packages, failed scans, and fixes to approve. Catching an active breach (not just a weakness) needs the monitoring layer above — silence doesn't guarantee safety.

Card checkout takes no money but creates real orders

What it is

When a customer pays by card or Google Pay, the site marks the order paid and gives loyalty points — but never actually charges anything. Only PayPal takes real money.

What someone could do
Any visitor can order your products, choose “Card”, and receive a real, fulfillable order plus loyalty points without paying a penny — no hacking, just normal use of the shop.
What to do
  1. Decide: switch card/Google Pay off for now (only PayPal takes money), or have me wire up real Stripe card payments.
  2. Until then, I’ll make the card path refuse to complete so no free orders can be created.
  3. Tell me which way to go — I’ll make the change and show you before it goes live.

Turning the fake path off is safe and I can do it now. Wiring up real Stripe card payments is a bigger change I’d want your go-ahead for first.

Anyone can view another customer’s saved address

What it is

A logged-in customer can load someone else’s account details by changing a number in the web address — the site doesn’t check the record belongs to them.

What someone could do
Read other customers’ names and delivery addresses — a privacy breach and, under UK data-protection rules, a reportable one.
What to do
  1. Nothing needed from you — the fix is applied.
  2. Push the change and let Vercel deploy so it goes live.

Things only you can do

Outside the code — your accounts & settings

I can’t click these for you, so here they are as plain steps. The first matters most.

1

Turn on two-factor auth (2FA)

On GitHub, Vercel, and Stripe. I can’t see whether it’s on, so treat it as off until you’ve confirmed it — the single most valuable thing on this page.

  1. Open each account’s security settings.
  2. Enable 2FA (an authenticator app beats text messages).
  3. Save the backup codes somewhere safe — not in your repo.
2

Rotate any leaked keys {{OMIT_IF_NONE}}

  1. Log into the provider (e.g. Stripe) and regenerate the exposed key.
  2. Paste the new key into Vercel → Settings → Environment Variables.
  3. Redeploy so the site uses the new key.
The rule for secrets: a secret key belongs only on your computer (.env.local) and in Vercel’s settings — never in the code, the repository, or the browser. If one turns up in the wrong place it’s removed and regenerated, because it may already have been copied.
