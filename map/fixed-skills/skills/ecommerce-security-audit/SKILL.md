# E-commerce Security Audit

Audit a website's code for security holes, explain each one in plain language a **non-developer owner** can act on, and apply fixes that actually close the hole — then help set up automation so the site stays checked over time.

Built for AI-generated e-commerce sites (Next.js/React on Vercel, paying through Stripe/PayPal/Google Pay, with an admin area) where the owner **cannot read code** and needs an honest, thorough second pair of eyes. The defining failure mode of these sites is scaffolding that was never finished — fake payment paths, controls left disabled, "demo" code shipped to production — so hunt for that as hard as for classic vulnerabilities.

---

## Read this first: the honesty contract

This skill's value depends on being truthful about what it can and cannot do. Never let a clean report imply "safe."

**What it reliably catches:** the common, high-impact flaws that actually get AI-built shops breached — prices trusted from the browser, fake/simulated payment paths, unverified webhooks, secret keys in the browser or repo, admin pages anyone can reach, one customer reading another's data, injection, disabled security controls, out-of-date packages. This is the majority of real incidents for sites like these.

**What it cannot do — state this plainly in every report:**
- It is **not a penetration test.** A pattern-and-logic review cannot find a novel flaw, or a clever chain of small weaknesses a skilled human would connect. For a live shop taking real money, recommend a professional pentest — this audit makes that cheaper, it does not replace it.
- It **cannot see outside the code** — account settings, the Vercel/Stripe dashboards, whether 2FA is actually on, whether a leaked key was already copied. Those become **owner actions**, never "verified."
- It is a **snapshot.** The site is clean today, not three changes from now. This is why the automation (below) exists.
- Some findings need **human judgement or professional advice** (business-logic abuse, legal adequacy of policies, whether an age-check method is legally sufficient). Flag these; do not certify them.

The three-ring model below encodes this: the skill *fixes* ring 1, gives *steps* for ring 2, and *advises* on ring 3.

## The AI-build lens (item 53) — a posture over the whole audit

These sites are generated by AI, which changes the threat: the AI makes hundreds of sourcing and coding decisions the owner can't see. Adopt this posture throughout — it's not a single check, it's how to read everything:
- **Assume the code was AI-generated** — so insecure patterns (items 8, 2, 22) may appear faster and in more places than a careful human would produce. Weight those checks harder.
- **Trust that nothing was finished.** AI leaves scaffolding in — fake payment paths, disabled controls, `DEV_OPEN_ACCESS` (item 22). Hunt unfinished scaffolding as a *category*, not a surprise.
- **Treat AI-chosen dependencies and snippets as untrusted until verified** — the AI can confidently install an abandoned, or even *hallucinated-then-maliciously-registered*, package (the concrete check lives in `dependencies.md` §4, rated 🔴).

There's a symmetry worth remembering: the builder and the checker are the same kind of tool. That's exactly why the honesty about limits matters — the checker shouldn't pretend to catch everything the builder might do. (This lens is fast-moving; see `MAINTENANCE.md` to revisit it often.)

## The three rings

Every finding belongs to one of three rings, and the skill's role differs in each. Keep them distinct in the report — a green ring 1 with an ignored ring 2 or 3 is still an insecure business.

- **Ring 1 — In the code (the skill fixes it).** Items 1–11, 22–24, 27–34, and the code-side backend items (43, 44, 45, 46, 47, 49, 50, plus the code half of 38/41). The skill finds, explains, and applies/proposes fixes.
- **Ring 2 — In the owner's accounts & habits (the skill writes the steps; the owner clicks).** Items 12–16, 35, the config-side backend items (37, 39, 40, 42, 48, and the owner half of 38/41), and third-space items 52 (team access) and 55 (domain/registrar). Own-account 2FA, key rotation, secrets discipline, login habits, deployment, DNS records, database exposure, encryption, tested backups, preview locking, CI secrets, team offboarding, registrar security. The skill cannot do these — it hands over plain, numbered steps.
- **Ring 3 — Decisions & outside reality (the skill advises and points onward).** Items 17–21, 25–26, backend item 51 (deep network/infrastructure → specialist), and third-space item 54 (incident readiness). UK GDPR & selling law, customer 2FA, third-party tools, drift over time, the pentest, regulated-goods legal sufficiency, cloud-infrastructure hardening, having an incident plan ready. The skill surfaces these honestly and says where a human is needed.

Item 53 (the AI-build lens) isn't ring-specific — it's a posture over the whole audit (see above), with one concrete 🔴 dependency check in `dependencies.md`.

## The workflow

Work in this order. **Do not** start rewriting the moment you spot something — for payment, login, admin, and money-logic code a hasty rewrite can break checkout or lock people out, which is its own damage.

1. **Orient.** What is this? Framework (Next.js App Router / Pages Router / other), where's the payment code, admin, login, DB calls, and which payment providers. If it's Next.js/Vercel (most AI sites), skim `references/nextjs-and-vercel-notes.md` — it changes where risky code lives. Detect *conditional* features early: does the site take **file uploads**? does the server **fetch user-supplied URLs**? does it embed any **AI feature** (chatbot, AI search, "ask about this product")? does it run **affiliate ads / click-through monetisation**? does the backend use **GraphQL** or parse **XML**? Those gate items 29, 30, 32, 36, 49, and 50. Also note the backend layer beneath the app (`references/backend-and-infrastructure.md`, items 37–51) — much of it is dashboard config, so plan for owner-actions there.

2. **Mechanical first pass — use the best scanners available.** Prefer `scripts/deep-scan.sh <repo>`, which runs professional-grade tools when present (OSV-Scanner, Trivy, `npm audit`, Semgrep, Gitleaks, retire.js) and falls back to the built-in `scan.sh` when they aren't — see `references/scanner-toolchain.md`. This is *especially* important for **old dependencies with known published vulnerabilities**, the most reliably catchable risk in AI-built code — treat a clean dependency scan as a pre-deployment gate. If the owner uses Claude Code, also recommend its native security layer (the free `security-guidance` plugin and `/security-review`) as a complementary always-on net. All read-only; a clean scan means "no obvious landmines," never "secure" — the deep money-and-data flaws (price tampering, unverified webhooks, IDOR, disabled controls, logic abuse) still need the manual review in step 3.

3. **Manual review, area by area.** Work the master list in `checklists/audit-checklist.md` in priority order, reading the matching reference for each area. Read the actual payment, auth, admin, and money-logic code — that's where the money literally is.

4. **Write the report.** Default to the clean HTML report — copy `templates/security-report.html`, fill in every `{{TOKEN}}`, and add one `<article class="finding ...">` block per finding (grouped Critical → High → Medium → Low). It's designed for a non-developer: plain-English first, colour-coded severity, numbered fix steps, and code tucked inside a collapsible "Developer detail" box. (A markdown version, `templates/security-report.md`, is available if the owner prefers plain text.) Obey the six reporting rules below either way. **Where the report goes: see "Where everything is written" below — never into the skill folder.**

### The first-scan notifications gate (required)

The automation only protects the owner if its alerts reach them. **On the first scan/report, surface "set up your security alerts email" as a prominent required action** (the HTML report has a dedicated gate callout) and treat it as a gate — don't present the security setup as complete until a dedicated alerts address exists and the sources (Dependabot, GitHub Actions failures, optional error-monitoring) are routed to it. Keep re-surfacing it on later runs until the owner confirms. Full steps and the honest "what email alerts can/can't tell you" caveat: `references/notifications-and-alerts.md`.

### Where everything is written (critical — read before creating any file)

The skill folder is **read-only reference material**. NEVER write anything into it — not reports, not scan output, not automation files. Everything the audit produces goes into the **project being audited**, so each project keeps its own audit trail and the base skill stays clean.

- Create a single top-level `.security-audit/` folder in the **project root** (create it if missing), with:
  - `.security-audit/reports/` — dated reports, e.g. `security-report-2026-07-10.html` (dated so each audit sits alongside the last, never overwriting).
  - `.security-audit/scan-results/` — dated raw `scan.sh` output.
- **Nothing audit-generated is ever committed or pushed.** Add `.security-audit/` to the project's `.gitignore` (create/append if needed). Reports and scan results describe the site's weaknesses — they must stay local only.
- **The one deliberate exception** is the GitHub workflow file for the weekly check (`.github/workflows/security-scan.yml`), which *must* live in the repo to run. It is safe to commit because it contains **no findings** — it only runs the scanner on a schedule and lets the job fail (which triggers GitHub's email). It must **not** write reports or scan output back into the repo. The local pre-commit hook is not committed. (Full details and files: `references/delivery-and-automation.md`.)
- In this hosted chat environment (no project repo on disk), save deliverables to `/mnt/user-data/outputs` and present them instead — the `.security-audit/` convention is for real project runs (e.g. Claude Code).

When running in a real project, tell the owner where the report was saved (`.security-audit/reports/...`) and that it's gitignored so it won't be pushed.

5. **Fix — propose first for money, auth, and access code.** For 🔴/🟠 findings in payment, membership, auth, admin, or money-logic code, **show the owner the change before applying it** — these break real transactions if done carelessly. For low-risk hardening (headers, dependency bumps, generic error messages) just apply it. After each fix state how to verify it. Never mark fixed what you haven't confirmed.

6. **Set up the automation (the layers).** See `references/delivery-and-automation.md`. Offer to set up: (0) **GitHub Dependabot** — the continuous, automatic "old vulnerable packages" watch (owner toggles alerts + security updates in repo settings; skill can add a findings-free `.github/dependabot.yml`) — highest-value, no skill needed; (1) a **pre-upload check** locally in `.security-audit/automation/` (gitignored) that blocks a commit containing a secret; (2) a **weekly + on-every-push GitHub check** — the one deliberately committed, findings-free workflow that never writes reports back; (3) this **on-demand audit** whose reports stay in gitignored `.security-audit/reports/`. **The tough dependency scan runs during every audit regardless of the owner's level** (deep-scan → OSV-Scanner), treated as a pre-deployment gate. Nothing that describes the site's weaknesses is ever pushed.

7. **Re-scan, confirm, hand over ring 2 & 3.** Re-run checks, give a before/after, and end with the owner's "things only you can do" list (rings 2 and 3).

**Optional advanced step — test the running site (DAST).** Beyond reading code, the *running* site can be attack-tested to catch live-behaviour and deployment issues a code review can't see. This is **opt-in and safety-gated**, not part of the default audit: it actively attacks the target, so it runs **only against a site the owner owns, never production** — a throwaway copy in a sandbox or an isolated staging deployment, with dummy/test credentials (Stripe test mode, disposable database, mocked services). See `references/dast-running-site.md` for the safety rules, how to stand up a throwaway target, and how to translate ZAP/Nuclei output into the plain-English report. Offer it; don't run it against anything real. It is NOT the check for old dependencies (that's the scanners) — it's the live-behaviour layer, sitting below a professional pentest on the ladder.

## The six reporting rules

Every report must satisfy all six. These are the contract with a non-developer owner.

1. **Plain-English first, code detail second and clearly separated.** Lead with what it is, what someone could do with it, and what to decide — in normal words. Put code, file paths, and commit hashes *underneath*, marked as the developer's section. Never in front of the owner.
2. **Easy language, step-by-step "what to do."** No finding is complete without numbered, plain steps — including owner actions (rotate a key, set a Vercel variable, turn on 2FA).
3. **Every finding rated** 🔴 Critical / 🟠 High / 🟡 Medium / ⚪ Low.
4. **Secrets model stated:** a key belongs only in local `.env.local` and Vercel's settings — never in code, repo, git history, or the browser. If found wrong: remove **and rotate** (assume it was copied).
5. **Owner 2FA surfaced every time.** The skill can't see it, so it always states 2FA on GitHub/Vercel/Stripe as mandatory, asks the owner to confirm each, and treats it as an open risk until they do. Customer-facing 2FA is separate and advisory.
6. **Honest about reach.** Separate "fixed for you" from "things only you can do." Never imply something was verified that lives outside the code.

A recurring lens that catches a whole class of these sites' problems: **flag anywhere the interface promises something the code doesn't deliver** — a checkout that confirms without charging, an age gate that claims verification it doesn't do, a returns promise with no policy, a cookie banner that ignores the choice. If the UI says it happened, confirm the code actually does it.

## Severity — in the owner's terms

Use these exact labels. "CVSS 7.5" means nothing to the owner; "someone can buy your products for £0" means everything.

- 🔴 **Critical** — Money can be stolen, customer data breached, or someone can take over the site/admin. Fix before launch, no exceptions.
- 🟠 **High** — Seriously exploitable and likely to be found. Fix before real traffic.
- 🟡 **Medium** — Real weakness, limited impact or needs specific conditions. Fix soon.
- ⚪ **Low / Hardening** — Good practice, defence-in-depth. Worth doing.

When unsure between two levels, round **up**. On a site taking payments, over-caution costs an afternoon; under-caution costs a chargeback storm or a breach notification.

## The boundary rule — what this skill does NOT chase

Staying sharp means not trying to be everything. This is a **security** audit.

- **Placeholder/broken/claimed-but-unreal code is flagged ONLY where it sits in a security-, money-, access-, data-, or legal-sensitive path.** A `status: "simulated"` in checkout is 🔴. A fake wishlist button that persists nothing is *not this skill's job* — it's a functional bug.
- **Explicitly out of scope** (may be *noted in passing*, never audited or certified): purely functional bugs (dead forms, fake success messages on non-sensitive features), **accessibility** (focus rings, WCAG — belongs to an accessibility skill), **performance** (N+1 queries, indexes, caching), and **ops/deploy reliability** (a broken `DATABASE_URL`, migration gotchas, the site being *down* — that's not a vulnerability).
- One light exception, as owner-awareness only: if there is **no logging / breach-detection at all**, add a single plain note that the owner currently can't tell if they've been breached, and that offsite **backups** are worth having. Not a code finding — just awareness.

If you notice out-of-scope issues, you may mention them in one line ("I also noticed some non-security things — happy to look separately"), but do not fold them into the security report or claim to have audited them.

## The fix protocol

Fixes must *actually close the hole* — that's the whole request.

- **Fix the root cause.** If the server trusts a browser price, compute the price server-side from the database — don't "validate that it looks reasonable."
- **Prefer the platform's safe path.** Stripe Payment Intents/Checkout, ORM parameterised queries, framework auth middleware, Vercel Blob for uploads — use secure-by-default patterns rather than hand-rolling.
- **Fail closed.** When a control can't run (missing key, error, unexpected value), it must **deny**, loudly — never silently allow. Apply this lens everywhere (see item 23).
- **Propose-first for money/auth/logic.** Payment, membership, auth, admin, and money-logic fixes are shown before applying. "Disable the fake path" vs "wire the real gateway" is a *product decision for the owner* — never auto-wire a payment integration. One safe auto-action: make a fake/simulated path **fail closed** (refuse and mark nothing paid) rather than fake success, while the owner decides.
- **Don't introduce a regression.** After a payment/auth fix, walk the happy path in words and confirm it still works.
- **Tell them how to verify.** Every fix ends with a concrete check: an attack that no longer works, a page that now redirects to login, a key gone from the browser bundle, `npm audit` clean.
- **Flag what you can't fix from code.** Key rotation, 2FA, Vercel env vars, Stripe dashboard config, bucket permissions — numbered owner to-dos.
